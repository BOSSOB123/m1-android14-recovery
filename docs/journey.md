# 从启动故障到可用的过程

## 记录的起点

用户将整个经历描述为“从无法进入安卓到 Android 14 成功”。现有可复核资料的技术起点，是一套曾运行正常的 Android 11 phh GSI 和它的恢复镜像；更早的原厂系统故障和 Android 11 安装经过并不完整。因此不能把缺失部分补写为已经证实的救砖步骤。

以下按阶段复盘，不用事后成功来掩盖当时的未知状态。

| 阶段 | 操作与观察 | 结论 |
| --- | --- | --- |
| 1. 整理 Android 11 备份 | 工作镜像尾部曾出现 dd 的统计文本；另取得精确 4 GiB 的 clean 镜像，记录 SHA256 和只读文件系统检查 | 只将 clean 文件视为恢复材料；文本污染不等于已证实为启动故障原因 |
| 2. Android 14 预检 | 核对静态 SAR、VNDK、展开长度、原机内核及旧 vendor；发现 data 使用 FDE | 保留旧加密 data 直接升级判 NO-GO |
| 3. 启动模式故障 | 进入 fastboot 后常规工具出现超时/unknown command；物理重启后卡固定启动画面或 Orange State | Android 14 此时尚未刷入，不能归因于 Android 14 写坏系统 |
| 4. 恢复通道排查 | USB 直读可获得部分 fastboot getvar；continue 模式切换不等于开机成功；继而建立 MTK Preloader/XFLASH 离线读取 | fastboot 能枚举不等于能可靠刷写 |
| 5. 离线备份 | 关键小分区备份完成；GPT CRC 核验通过；核对原机 boot/vendor/当前 vbmeta | 有恢复材料，但还未实测恢复启动 |
| 6. 用户数据取舍 | 全分区读取慢且得到的是加密块；用户明确选择不保留应用和个人文件，只保留系统恢复材料 | 停止全量 data 备份；残缺文件明确标记不可恢复 |
| 7. 镜像完成核验 | 完整 XZ 解码，实际 raw 长度、ext4 检查、本地 SHA256、VNDK 28 APEX、内嵌签名检查完成 | 达到实验刷写的技术准备条件；不代表保证兼容 |
| 8. 明确授权 | 列明只写 system、之后清除 userdata/metadata，以及失败时系统回退范围 | 用户明确同意后才执行破坏性步骤 |
| 9. 初次写入失败 | 初次记录在 system write failure 停止，没有继续清除 data | 写入中止可能留下部分更新的 system，不能视作“设备完全未变” |
| 10. 传输修正并重试 | 使用原机 boot1 中的 EMI 初始化 DRAM；工作区串口包装器处理分块发送与握手期限 | 该路径与本台设备及所用 mtkclient 版本绑定 |
| 11. Android 14 写入验证 | 写入与完整读回 SHA256 一致；按授权清除 data/metadata；GPT、vbmeta 写前后保持一致 | 仅确认存储操作完成，此时仍不能宣布开机成功 |
| 12. 首次开机 | 物理电源复位后经过 Orange State；用户看到安卓，ADB 报告 API 34 与 boot_completed=1 | Android 14 首次启动成功 |
| 13. 基础系统检查 | 检查时间、联网状态提示与显示性能 | 逐项验证，仍保留蓝牙等问题 |

## 仍不能下的结论

- 没有证据证明早期卡启动画面的唯一根因是 BCB、某个 APK、Orange State 或备份尾部文本。
- 在 BCB 中读到 bootonce-bootloader 并不足以证明它造成了故障；本次没有为此改写 BCB。
- expdb 中的历史原厂日志不能用来判断当前 vbmeta 或锁状态。
- 最终用户报告可正常使用，不等于已经完成长时间稳定性、电池、蓝牙和全部媒体路径验证。

## 数据处理的教训

分区长度不是“有用文件”的大小。全量镜像会读取空闲块和加密块；文件级备份需要可解密、可挂载且一致的文件系统。残缺的 userdata 镜像不可当成有效恢复备份。丢弃 data 必须是机主的明确选择，而不是为了省备份时间默认代替机主决定。
